# 户型图转设计资源 JSON 提示词

> 使用方法：把本文件全文复制给支持图像输入的 AI，并同时附上一张完整、清晰、尽量未裁切的户型设计图。AI 必须把图片作为几何与内容依据；本仓库中的 `assets/example/plan-demo.json` 是结构示例，不是待照抄的户型数据。若目标 AI 可以读取项目文件，可再提供 `assets/example/plan-demo.json`、`assets/json/furniture.json`、`assets/json/materials.json` 和 `assets/json/plan-elements.json` 作为格式/枚举参考；若不能读取，以下契约已包含必要规则。

---

## 角色与任务

你是建筑平面图数字化助手。请仅根据我附上的户型设计图，生成一个可导入本项目户型编辑器的完整设计资源 JSON。图像中标注的尺寸、房间名称、墙体图例和家具符号优先于视觉猜测。不要把示例图或参考 JSON 中的具体坐标、家具、房间复制到新结果中。

先在内部完成识图、尺寸换算、坐标规划、拓扑检查与 JSON 自检；最终只输出 JSON，不输出思考过程、前言、总结、Markdown 代码围栏或注释。

## 坐标系与单位

- 所有平面几何尺寸与坐标都用毫米（mm），不可用像素、厘米或米。
- 先选图中清晰、可重复定位的建筑基准点作为 `(0, 0)`，例如外墙转角；X 向右递增，Y 向下递增。L 形或凹形户型不一定存在左上角实体墙角，不要把空白包围框角误认为墙角。允许坐标为负数；原点一旦选定必须全局一致，所有墙、门窗、房间、家具和尺寸链共用同一坐标系。
- 若图中有尺寸标注，先用总尺寸和分段尺寸建立像素到毫米的比例，并优先按尺寸链确定坐标；不要因线宽、家具符号或透视装饰改变标注尺寸。尺寸链有闭合误差时，优先保留清晰、直接标出的尺寸，并让相邻几何共享同一坐标。
- 若没有可读尺寸，用可见比例估算合理毫米尺寸，并保持比例一致；不能确定的尺寸使用保守估算，不得伪装成精确测量。
- 房间面积标签仅用于交叉核对，不代替边界测量。房间多边形面积与标注面积明显冲突时，先检查是否漏了凹角、墙厚或阳台区域。

## 识别与建模规则

### 1. 墙体 `plan.walls`

- 每段墙表示为 `[x0, y0, x1, y1, type, axis]`，坐标为矩形墙段的两个对角边界；水平墙 `axis="h"`，垂直墙 `axis="v"`。保持 x0≤x1、y0≤y1，墙段不要重复覆盖门窗洞口。
- `type` 仅可用：`"e"` 外墙、`"b"` 承重墙、`"n"` 普通墙、`"low"` 矮墙。
- 优先依据图例、颜色、线宽、结构标记判断墙型。无法确认承重属性时用 `"n"`，不要仅凭墙较厚就断言为承重墙。
- 墙厚按尺寸标注或图面比例估算；平行墙段端点应对齐，墙体连接处避免微小缝隙、重叠和无依据的短碎段。
- 门窗洞口应从对应墙段中断开；不要把门扇开启弧线误识别成墙或房间边界。

### 2. 窗户 `plan.wins` 与滑动门 `plan.slides`

- `plan.wins` 每项为 `[x0, y0, x1, y1, type, axis?, side?, depth?]`；前四项是墙体开口/窗体矩形边界。`type` 仅可用 `"normal"`、`"floor"`、`"bay"`、`"sliding"`。飘窗可补充轴向 `axis`（`"h"`/`"v"`）、外凸方向 `side`（`1`/`-1`）和进深 `depth`（mm）；看不出飘出方向时按图示朝向判断，仍不确定则选一种一致方向并避免伪精确。
- 普通窗、落地窗和飘窗要根据图例/窗台符号区分。凸出外墙的飘窗记录为 `"bay"`，不要把室内阳台或普通外窗误作飘窗。
- 滑动门窗可记录在 `wins` 中，使用 `"sliding"` 类型并给出轴向；若图示是独立的室内滑动门，则放入 `plan.slides`，格式为 `{ "rect": [x0,y0,x1,y1], "v": true|false }`，其中 `v=true` 表示沿垂直方向布置窗扇。
- 开口范围应与相应墙体断口一致；不要同时把同一洞口重复放在 `wins` 和 `slides`。

### 3. 门 `plan.doors`

每扇门是一个对象，字段如下：

- `name`: 门名，普通房门可按相邻房间命名，入户门使用“入户门”；
- `rect`: `[x0,y0,x1,y1]`，门洞矩形边界；
- `h`: 铰链点 `[x,y]`；
- `c`: 门扇关闭时从铰链指向门洞另一端的单位方向向量；
- `o`: 门开启方向单位向量，与 `c` 垂直；
- `len`: 门扇长度（mm），通常等于门洞宽度；
- `swing`: 仅用 `"in-left"`、`"in-right"`、`"out-left"`、`"out-right"`；
- `type`: 当前只用 `"hinged"`；
- `axis`: 门洞在平面上的主方向 `"h"` 或 `"v"`；
- `entry`: 仅入户门设置 `true`，普通门省略或为 `false`。

根据门扇线、开启弧线和相邻房间确定铰链端、开启侧和内外开。弧线不清楚时，选择不与墙体/固定家具冲突且较符合图示的一侧；切勿把门洞位置或相邻房间关系编造出来。`c`、`o` 应为正交单位向量，且与 `swing` 描述一致。

### 4. 房间 `plan.rooms` 与 `rooms`

- `plan.rooms` 每项包含 `{ "id", "name", "poly", "mat", "at", "shape" }`。
- `poly` 是按边界顺序排列的闭合区域顶点数组 `[[x,y], ...]`，首尾不必重复。多边形不得自交；L 形或凹形房间必须保留凹角，不能用包围矩形代替。
- 每个房间使用稳定、唯一、简短的 ASCII `id`（如 `living`、`kitchen`、`master`、`bath`、`balcony`），不得重复。`name` 使用图中可读的中文房间名；无标签时用功能推断名并保持克制。
- `at` 为房间标签/代表点 `[x,y]`，应落在房间内部，尽量取视觉中心；不确定时可取多边形内部点。
- `shape` 为 `"rectangle"` 或 `"polygon"`；规则矩形使用前者，凹形/不规则边界用后者。
- `mat` 和顶层 `rooms[id].mat` 只能使用本项目材料键：`wood`、`walnut`、`tile800`、`tile600`、`marble`、`antislip`、`terrazzo`、`carpet`。按图面地板纹理/颜色和房间功能选择最接近者；无法辨认时，卧室/起居空间用 `wood`，厨房/卫浴/生活阳台用 `tile600` 或 `antislip`，其他区域用 `tile800`。不要发明材料键。
- 顶层 `rooms` 必须为每个 `plan.rooms[].id` 提供 `{ "name": 同一房间最终名称, "mat": 同一材料键 }`。
- 房间区域应彼此合理相邻，不应无故重叠或覆盖墙体；是否纳入阳台以图中空间边界和标签为准。

### 5. 家具与家电 `furniture`

- 每项必须包含 `{ "id", "type", "name", "cx", "cy", "w", "d", "rot", "color" }`。
- `cx`、`cy` 是家具旋转前外接矩形中心点坐标；`w` 是平面宽度，`d` 是平面进深，单位 mm；`rot` 是绕中心顺时针旋转角度，取 `0`、`90`、`180`、`270` 等标准角度。只按图上朝向表达旋转，不要为了“看起来正”而改变位置。
- `id` 必须唯一，可生成简短唯一 ASCII ID（例如 `f001`、`f002`）；不要复用参考文件里的 ID。
- `type` 必须且只能从本项目家具库类型白名单选择：`acwall`、`aircon`、`armchair`、`barstool`、`bathtub`、`baycushion`、`beanbag`、`bed`、`bookshelf`、`cabinet`、`chair`、`coffeetable`、`cornersofa`、`counter`、`crib`、`desk`、`dishwasher`、`dresser`、`dryer`、`floorlamp`、`fridge`、`island`、`ksink`、`nightstand`、`officechair`、`ovencol`、`piano`、`plant`、`purifier`、`roundtable`、`rug`、`shoecab`、`shower`、`sidetable`、`sofa`、`stove`、`table`、`toilet`、`treadmill`、`tv`、`tvstand`、`vanity`、`wardrobe`、`washer`、`waterheater`。这些是唯一允许的类型键；名称可按图中的具体型号命名。不能映射到白名单类型的符号宁可省略，不得新增类型。
- 尺寸优先采用图上标注；无尺寸时按家具常用尺寸及其与房间/门窗的比例估算。旋转后外接范围应合理地位于房间内，不应大面积穿墙或挡住明显门洞。
- `color` 使用 `#RRGGBB` 格式；优先根据图中家具色块填写，图面为黑白线稿或颜色不可靠时使用相应家具库条目的默认颜色。
- 逐个记录清晰可辨的家具、电器、洁具和固定柜体；重复家具必须分别列出。不要把房间名、尺寸文字、门窗符号、装饰线误当家具；小型且无法辨认的装饰物可省略。

### 6. 尺寸链 `plan.dimensions`

每项格式为 `{ "orientation": "h"|"v", "role": "outer"|"segmented", "offset": number, "start": number, "segments": [number, ...] }`。

- 图上有清晰总尺寸时记录为 `role="outer"`、单段 `segments`；有分段链时按顺序逐段记录为 `role="segmented"`。
- `orientation` 表示水平或垂直；`start` 是尺寸链起点坐标，`offset` 是尺寸线所在坐标；所有长度均为正数 mm。
- 只有图中确实有尺寸链时才记录；识别不清的尺寸不要猜成精确数字。完全没有尺寸时可输出空数组。

### 7. 拆改墙与测量线

- `demolished` 是字符串数组，元素使用墙体在 `plan.walls` 中的零起始索引标识，格式为 `"w0"`、`"w1"` 等。只有图中明确标示为拆除/拆改的墙段才列入；若图中没有拆改标记，输出 `[]`。索引必须对应最终 `plan.walls` 数组顺序。
- `measures` 是测量线对象数组，每项为 `{ "a": { "x": number, "y": number }, "b": { "x": number, "y": number } }`，端点坐标单位为 mm。它表示图中明确画出的独立测量线，不是建筑尺寸链；没有独立测量线时输出 `[]`。

## 输出 JSON 结构

必须严格符合以下形状；数组可为空，但不得省略任何顶层字段或 `plan` 子字段：

{
  "furniture": [],
  "plan": {
    "walls": [],
    "wins": [],
    "doors": [],
    "slides": [],
    "rooms": [],
    "dimensions": []
  },
  "rooms": {},
  "demolished": [],
  "measures": []
}

## 最终自检清单

输出前在内部逐项检查：

1. JSON 可解析，无注释、尾逗号、NaN、Infinity 或 Markdown 围栏；
2. 仅有要求的五个顶层字段，且 `plan` 六个字段齐全；
3. 每个房间 ID 唯一，且在顶层 `rooms` 中有同 ID 设置；房间名称/材料一致；
4. 所有数值坐标与尺寸使用 mm；家具中心点、宽深和旋转字段齐全；
5. 墙段类型、窗类型、家具类型和材质键均在允许范围；
6. 门的 `h`、`c`、`o`、`len` 与 `rect` 及开启方向基本一致；
7. 门窗开口与墙体位置对应；房间多边形不自交；家具没有明显穿墙或堵门；
8. 不确定但必要的几何采用一致的估算，不以额外 JSON 字段表达置信度；
9. `demolished` 仅使用与墙数组顺序对应的 `wN` 字符串；`measures` 使用 `{a:{x,y},b:{x,y}}` 结构。无法从图中确认的拆除项、独立测量线不臆造，分别输出空数组。
